## Q1: How do you pass data between the goroutines?

### 1. Channels (The Idiomatic Approach)
Channels are the primary way to communicate between goroutines in Go, following the philosophy: *"Do not communicate by sharing memory; instead, share memory by communicating."*

*   **Unbuffered Channels:** These provide synchronous communication. The sender blocks until the receiver is ready, and vice versa. This ensures strict synchronization.
*   **Buffered Channels:** These allow the sender to continue execution as long as the buffer is not full. This is useful for decoupling the producer and consumer speeds.

```go
package main

import "fmt"

func producer(ch chan<- int) {
    for i := 1; i <= 3; i++ {
        ch <- i // Send data to channel
    }
    close(ch) // Always close channels to signal completion
}

func consumer(ch <-chan int) {
    for val := range ch { // Receive until channel is closed
        fmt.Println("Received:", val)
    }
}

func main() {
    ch := make(chan int) // Unbuffered channel
    go producer(ch)
    consumer(ch)
}
```

### 2. Shared Memory with Mutexes
When multiple goroutines need to access and modify a shared data structure (like a map or a struct), you must use synchronization primitives from the `sync` package to prevent **race conditions**.

*   **`sync.Mutex`:** Provides mutual exclusion. Only one goroutine can hold the lock at a time.
*   **`sync.RWMutex`:** Optimized for scenarios where you have many readers but few writers. Multiple goroutines can read simultaneously, but a writer gains exclusive access.

```go
package main

import (
    "fmt"
    "sync"
)

type SafeCounter struct {
    mu    sync.Mutex
    value int
}

func (c *SafeCounter) Increment() {
    c.mu.Lock()         // Acquire lock
    defer c.mu.Unlock() // Ensure lock is released
    c.value++
}

func main() {
    counter := &SafeCounter{}
    var wg sync.WaitGroup

    for i := 0; i < 100; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            counter.Increment()
        }()
    }

    wg.Wait()
    fmt.Println("Final Counter:", counter.value)
}
```

### 3. Atomic Operations
For simple primitive types (integers, booleans, pointers), the `sync/atomic` package provides low-level, hardware-supported atomic operations. These are generally faster than mutexes because they do not involve context switching or blocking the OS thread.

*   **Use Case:** High-performance counters, flags, or state indicators.

```go
package main

import (
    "fmt"
    "sync"
    "sync/atomic"
)

func main() {
    var ops uint64
    var wg sync.WaitGroup

    for i := 0; i < 1000; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            atomic.AddUint64(&ops, 1) // Atomic increment
        }()
    }

    wg.Wait()
    fmt.Println("Total Operations:", atomic.LoadUint64(&ops))
}
```

### Summary Comparison

| Method | Best Use Case | Pros | Cons |
| :--- | :--- | :--- | :--- |
| **Channels** | Passing ownership of data or coordinating workflows. | Thread-safe by design; prevents most race conditions. | Can be slower due to overhead/scheduling. |
| **Mutexes** | Managing complex shared state (maps, structs). | Very flexible for complex data structures. | Risk of deadlocks and race conditions if not careful. |
| **Atomics** | Simple counters or flags. | Extremely high performance. | Limited to primitive types only. |
| **Context** | Signaling cancellation or passing request-scoped metadata. | Standardized way to handle timeouts/interrupts. | Not intended for passing large amounts of application data. |
