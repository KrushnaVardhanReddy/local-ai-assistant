You are tasked with implementing a Dynamic Reading Cooldown for Live Mode Auto-Submit in BarnOwl AI (P72-T5).

════════════════════════════════════════════════════════════════
TASK CONTEXT
════════════════════════════════════════════════════════════════

In Live Mode, the STT pipeline automatically feeds transcript chunks to the `QuestionBuffer`. Once the Llama classifier (Gemma) identifies a complete question, it auto-flushes and triggers the LLM. 

The problem: After the LLM generates a response, the user needs time to read it. If the interviewer speaks immediately, the microphone picks it up, the buffer classifies it, and it triggers the LLM again instantly — wiping the user's screen before they finish reading.

Additionally, the Gemma classification step currently has a strict 3-second context timeout, which frequently results in "context deadline exceeded" errors when the local machine is under load.

Your goal is to implement a dynamic "Reading Cooldown" that pauses auto-triggering *without* dropping the interviewer's audio, and to fix the classification timeout.

FILES TO CREATE / MODIFY
════════════════════════════════════════════════════════════════

[MODIFY] wails-app/core/engine/engine.go
[MODIFY] wails-app/core/engine/pipeline.go
[MODIFY] wails-app/backend/classifier/buffer.go

DETAILED SPECIFICATION
════════════════════════════════════════════════════════════════

─── CHANGES TO wails-app/core/engine/engine.go ────────────────────────────────

1. Add a `lastResponseAt time.Time` field to the `StealthEngine` struct.
2. We do not need a hardcoded duration field since we will calculate the cooldown dynamically.

─── CHANGES TO wails-app/core/engine/pipeline.go ────────────────────────────────

1. Locate the `triggerLLMWithQuestion` function. At the very end of the successful LLM stream (where it stores the response in the cache), count the number of words generated in `finalAns`.
2. Calculate a dynamic cooldown: `wordCount * 300 * time.Millisecond`.
3. Clamp this cooldown duration so it is never less than `3 * time.Second` and never more than `20 * time.Second`.
4. Stamp `e.lastResponseAt = time.Now().Add(cooldown)` immediately after calculating it. Be sure to lock the mutex `e.mu` when writing to `e.lastResponseAt`.

─── CHANGES TO wails-app/backend/classifier/buffer.go ────────────────────────────────

1. We need to pause the auto-flush while the cooldown is active. Add a `IsCooldownActive func() bool` callback to the `QuestionBuffer` struct, or expose a method to let the engine pause it. 
   - Alternatively, you can just check the engine's `lastResponseAt` inside `pipeline.go` before routing the chunk to the buffer, but we MUST STILL buffer the transcript without flushing.
   - The cleanest approach: In `pipeline.go`'s `handleTranscript` function, if `time.Now().Before(e.lastResponseAt)` is true, you can route the `cleanTranscript` into `e.questionBuffer.AddChunk(cleanTranscript)`, BUT you must ensure the buffer *does not trigger the classifier or auto-flush*. 
   - To achieve this, modify `QuestionBuffer.AddChunk` in `buffer.go` to accept an `ignoreClassifier bool` parameter, or create a `AddChunkSilently` method that only appends to the internal `b.chunks` slice without triggering the `b.classifyFn` goroutine.

2. Increase Context Timeout:
   - In `buffer.go`, locate the `ctx, cancel := context.WithTimeout(context.Background(), 3*time.Second)` call inside `AddChunk` (or wherever the classification is triggered).
   - Change `3 * time.Second` to `10 * time.Second` to prevent "context deadline exceeded" errors when Gemma is slow.

─── MANUAL OVERRIDE LOGIC ────────────────────────────────

1. If the user clicks "Submit Answer" (which calls `FlushQuestionBuffer`), or types a manual chat follow-up, it should bypass any active cooldown immediately and trigger the LLM.
2. Ensure `e.lastResponseAt` is zeroed out or ignored when manual triggers occur.
